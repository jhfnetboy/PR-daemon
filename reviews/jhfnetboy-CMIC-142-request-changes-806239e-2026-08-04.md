This is a genuinely strong planning-doc set — internally cross-referenced, machine-verifiable acceptance criteria on every Task, an explicit PII boundary section, and a documented Codex-review-and-fix history already baked in. The issues below are internal-consistency defects between the **design doc** (`docs/design/agent-interaction-v2.md`) and the **spec/tasks docs** it was supposedly finalized from — three places where the design doc still says the opposite of what spec.md/tasks.md correctly settled on, plus a couple of spec-level gaps. Because these documents are the literal source implementers will code from, an unresolved contradiction here becomes a real bug once someone builds T1.5.1 / T2.3.0 / T2.3.1 / T4.1.1 off the wrong instruction.

### Blocking

1. **[Med] docs/design/agent-interaction-v2.md §6.3 vs spec.md §1 / tasks.md T2.3.1 — address routed to the wrong table.** §6.3 says the sampling confirmation page submits the address and "落 `leads` / 生成待办", but spec.md §1 explicitly carves shipping address OUT of `leads` ("⚠️ 收货地址【不在这里】"), and tasks.md T2.3.1's own 依赖 line says "地址落 `sampling_requests`，不落 `leads`". An implementer following the design doc literally writes PII into a table whose role-strip matrix doesn't cover it. **Fix**: change §6.3 to "落 `sampling_requests`（见 spec.md §4）".

2. **[Med] docs/design/agent-interaction-v2.md §3.6 — "Email 只在交付点要" contradicts the doc's own decided policy.** §3.6 (the literal prompt-rewrite source for T1.5.1) tells the new SYSTEM prompt to ask for email "at the delivery point" — but §2 and the §8 decision table (both same file, stated multiple times) mandate "AI 一个字都不提 email" because it's already captured at invite-only registration. **Fix**: delete the phrase; replace with "永不询问 email（纯邀请制，注册已取得）".

3. **[Med] docs/design/agent-interaction-v2.md §3.6 — "第 5 轮起主动收口" contradicts §3.5 / §8 decision #11.** §3.5 and decision #11 explicitly killed forced closure ("否掉强制收口，AI 永不催客户"); §3.6 still tells the new prompt to actively close from round 5. tasks.md already reflects the corrected behavior — the design doc is the one lagging. **Fix**: reword to "轮次账只约束 AI 自己别车轱辘话，不做任何收口动作".

4. **[Med] docs/agent/tasks.md T2.3.0 / T4.1.1 — new PII tables don't list `scripts/no-real-pii.sh` in scope.** spec.md §0 (D-7) hard-requires "新 PII 表必须在建表的同一个 PR 里进 `scripts/no-real-pii.sh` 扫描范围" — but neither Task's 开发范围/涉及文件 lists that script (T4.1.1's acceptance command *invokes* it as if already covering the new table — a false sense of coverage). Contrast with T3.1.1 (leads), which correctly lists it in both places. **Fix**: add `scripts/no-real-pii.sh` to both Tasks' 涉及文件 and make "add new table to scan scope" an explicit dev-scope line, per T3.1.1's pattern.

5. **[Med] docs/agent/tasks.md T4.1.1 / T4.1.2 — the doc's strongest architectural rule has zero Task coverage.** spec.md §3 states: "聚合视图和明细视图是**两个端点**，不是同一个端点加过滤" plus a sales-scoped `WHERE lead_id IN (...invited_by=me.id)` requirement for `open_questions`. Neither Task's dev scope or acceptance criteria mention role-based visibility, sales-scoping, or endpoint separation — T4.1.2's only assertions are sort order and mark-resolved behavior. **Fix**: T4.1.2 dev scope should explicitly require two endpoints; acceptance should add "production/purchasing 端点响应不含 lead_id/inquiry_id" and "sales-A 读不到 sales-B 名下的 open_question".

6. **[Med] docs/agent/spec.md §4 / tasks.md T2.3.0+T2.3.2 — `fee_usd` unit mismatch.** Column is `fee_usd INTEGER` with comment "生成时的打样费(分)" (i.e. cents) — but T2.3.0 says it stores "当时从费用表取到的值", and T2.3.2 says the fee table's current entries are all literally `59`. Implemented as written, `59` (dollars) lands in a column documented as cents → the row reads as $0.59. **Fix**: rename to `fee_cents` (store `5900`) or fix the comment, and add an explicit unit assertion to T2.3.0's acceptance command.

7. **[Med] docs/agent/spec.md §1 — `leads.email` has no uniqueness constraint, contradicting the table's own stated purpose.** §1's rationale for the table is "粒度=一个人" and "老客户复购" (repeat-customer tracking) as the exact signal it exists to preserve — but `idx_leads_email` is a plain (non-unique) index. **Verified against the actual repo**: `apps/api/src/invites.ts:114`'s `registerCustomer` reuses an existing `users` row by email, but `users.email` itself has no UNIQUE constraint either — a second invite-registration (especially from a different `sales`) on the same email produces a second `leads` row with a different `invited_by`, splitting the "repurchase" history the table exists to track, and putting that person's PII under two different sales' "只看自己邀请的 lead" scope simultaneously. **Fix**: add `UNIQUE(email)` (or `UNIQUE(user_id)`) + upsert semantics; T3.1.1 acceptance should assert "same email re-registered → no second row".

*(All 7 above were independently found by Opus R2 reading the diff cold, then adversarially challenged by Codex R3 with verbatim excerpts inline — Codex confirmed 6/6 of the ones it was fed, with #4 sharpened from "inconsistency" to "directly violates the doc's own stated hard rule". #6 and #7 came from Opus R4's full-diff pass, #7 backed by reading the actual `invites.ts`.)*

### Suggestions

- The design doc's header still reads "状态：设计稿，待评审" (draft, pending review) while spec.md/roadmap.md/progress.md all treat it as finalized. Add a line: "已定稿；与 `spec.md` 冲突时以 `spec.md` 为准" — all three Blocking design-doc contradictions above stem from readers not knowing which document wins.
