## Blocking — the rebuild introduced new data corruption

**[High] `dist/api/search.json:1`** — the rebuild injected 3 task records that have **no source anywhere in this repo** at `882f87a` (`backlog/tasks/` tops out at `task-38`; `git ls-tree -r 882f87a` confirms none of task-39/44/48 exist in this tree): a **malformed record** — `id:"TASK-"` (missing number), `title:""`, `status:""`, `assignee:[]` — whose `rawContent` field nonetheless holds the full raw markdown of a task called "TASK-39", plus two well-formed but equally sourceless records TASK-44/TASK-48. Since `dist/` is committed and deployed as-is (no CI build step per `AGENTS.md`), this malformed entry ships to the live search index. Root cause verified: task-39's YAML frontmatter title is `title: Fix /sync-progress fabrication: gh-api 200-OK validation before write` — the unquoted `: ` inside the scalar is invalid YAML (`yaml.safe_load` raises `ScannerError: mapping values are not allowed here`), so whatever parser the export pipeline uses silently emits blank metadata while still dumping the raw text.
**Fix:** quote that frontmatter title wherever task-39 actually lives, rebuild `dist/` against a verified-clean server, and re-diff before committing.

**[High] `dist/api/statistics.json:1`** — three different "how many tasks" numbers now ship together in one snapshot: `statistics.totalTasks=39`, `dist/api/tasks.json` has exactly 37 entries, `dist/api/search.json` has 40 `type:"task"` entries. At the prior head all three agreed (37/37/37). `statistics.recentActivity.created` embeds the leaked TASK-44/TASK-48 records verbatim, and they drive every other changed number (`statusCounts["To Do"]` 15→17, `priorityCounts.low` 13→15, `completionPercentage` 19→18, `averageTaskAge` 93→123 — the last is a directionally implausible jump for a rebuild that only legitimately added 2 tasks, corroborating contamination rather than a math bug).
**Fix:** add a post-build assertion — `statistics.totalTasks == len(tasks.json) == count(search.json, type=="task")` — hard-fail the build otherwise.

**[Medium] `scripts/export-backlog.js:8,94-99`** — `const PORT = 8422` is hardcoded; the local backlog server is spawned with `stdio:'ignore'`, no `'error'` handler, no exit-code check, and no readiness/identity probe — just a fixed 4-second sleep before scraping. A separate `backlog browser -p 8422` instance (PID 2777, running continuously since 2026-07-07, bound to a *different* local checkout of this same repo with 49 task files vs this tree's 38) is the strongest available explanation for where TASK-39/44/48 leaked in from — though note: `tasks.json` came back with exactly *this* branch's correct 37 ids rather than the other checkout's set, an asymmetry that isn't fully explained by a simple "wrong server answered everything" story (all endpoints share the same `fetchFromLocal(8422)` call per the code), so the port-collision mechanism is well-supported but not 100% pinned down.
**Fix:** bind an ephemeral free port (or preflight-check 8422 and abort with a clear error), attach `server.on('error')`/exit handling, and verify the served task set matches local `backlog/tasks/*.md` before fetching anything else.

**[Medium] `docs/ECOSYSTEM_MAP.md:63`** — `### 全部仓库（26 个）` for the AAStarCommunity org against exactly 30 actual table rows in that section. This commit is titled "仓库计数纠偏" (repo-count correction) but its only hunk in this file is the iDoris.ai section (`@@ -101,12 +101,12 @@`) — line 63 was never touched, and the same wrong `26` also appears at `docs/ECOSYSTEM_MAP.md:31-32`'s local-path convention table, while the iDoris.ai fix left its own duplicate wrong number (`12`) standing two sections above the row it corrected (13 rows). The count-fix pattern is applied inconsistently within the same file.
**Fix:** pick one true number per org (or generate from `gh api orgs/*/repos`) and apply it everywhere the count is stated, not just the row that happened to get touched.
