## PK Review v4 — incremental round 8 (commit `485fd30`, since last-reviewed `6246a0f`)

**Verdict: REQUEST_CHANGES**

This round switches the production mutual-exclusion primitive from a hand-rolled symlink CAS (which needed correction across 5 straight rounds) to Linux `flock(1)`, keeps the symlink CAS as a macOS dev/test-only fallback, closes an fd-9-inheritance gap for user-configurable hooks, and hardens `cmd_recovery` to hard-fail (`LOCK_FATAL=1`) instead of silently `exit 0`ing on lock contention. The direction is right — flock is categorically simpler and safer than the hand-rolled CAS — but the migration itself introduces a new production-only regression, and the two new tests meant to validate the new production path cannot actually catch a broken implementation.

All findings below were independently reproduced by **three separate reviewers** (Opus R2's own empirical repro in a throwaway worktree, Codex R3's adversarial pass with its own independent stub-`flock` repro run via real `codex exec` inside a git worktree checked out at PR head, and Opus R4's 4th independent repro during final verdict) plus the Sonnet-executor's own initial repro — convergent, not single-source.

### Blocking

1. **`exec 9>"$AU_STATE_DIR/lock.flock" 2>/dev/null` permanently clobbers this shell's stderr for the rest of the run, on the production flock path** (`aastar-node-updater.sh:240`). Because this `exec` has no command name, *both* redirections bind to the current shell permanently, not just to the open attempt — this is standard bash `exec`-with-redirections-only semantics. Practical effect: every subsequent `warn()`/`die()` (which write via `echo ... >&2`) and all curl/tar/minisign/systemctl stderr is silently discarded for the remainder of the process — **including the very next line's own contention message** (`另一个 updater 实例持锁(flock)`). Empirically reproduced **four independent times** (Opus R2, Sonnet executor, Codex R3 with its own stub `flock`, Opus R4 with a minimal bash repro) on this flock-less macOS dev box by forcing the production branch: `apply <ver>` against a manifest with no matching release → exit 1, stdout has the expected log/notify lines, **stderr capture file = 0 bytes**. This means production boards will have zero stderr/journal signal for update failures on the new locking path — the opposite of what boot-recovery observability needs. Fix: scope the suppression to just the open attempt with a brace group: `if ! { exec 9>"$AU_STATE_DIR/lock.flock"; } 2>/dev/null; then lock_contended "无法打开锁文件"; fi`. `cleanup()`'s `exec 9>&- 2>/dev/null || true` (`:186`) has the identical no-command shape — verified its blast radius is much smaller (only fires when `LOCK_FD_HELD=1`, i.e. only after stderr is already dead on that path, and only at EXIT — it just masks a `rm -rf "$WORK"` failure) but fix it in the same pass for consistency.

2. **Cross-version split-brain reintroduced for the symlink→flock migration itself** (`aastar-node-updater.sh:238-243`). The production flock branch returns immediately after `flock -n 9` and never inspects `$LOCK_LINK` (the old symlink lock path) at all. The pre-existing legacy-holder check ("老格式锁仍活…升级切换中?") now lives *only* inside the fallback branch, which production never enters — so an in-flight instance of the **previous** updater version (pre-this-PR code, still holding `$AU_STATE_DIR/lock` as a symlink) is completely invisible to a new flock-based instance: both proceed and mutate `current`/`state.json` concurrently. This is exactly the mkdir→symlink migration hazard this code already guards against, silently reintroduced for symlink→flock. Realistic trigger: the updater script isn't under the versioned `current` tree (replaced directly by operator deploy), so a manual `apply <ver>` right after dropping the new script, while a timer-triggered `check` from the *old* script is still mid-`curl --max-time 300`, lands in this exact window. Fix: on the flock path, after acquiring the flock, also check the legacy symlink/mkdir surface (`oldpid="$(readlink "$LOCK_LINK" ...)"; lock_holder_alive "$oldpid" && lock_contended "旧版 updater 仍持 symlink 锁(升级切换中)"` + the `[ -e ] && [ ! -L ]` mkdir case) for at least one release cycle.

### Should fix

3. **New test T57 ("生产路径 flock…真互斥") is vacuous on both its assertions** (`test-updater.sh:1036-1050`). (a) The manifest has `releases:[]`, so `apply 0.99.0` dies with "manifest 里没有版本" *after* acquiring the lock, regardless of whether the lock excludes anything — verified with **zero** contention involved: a plain uncontended run against the same empty-release manifest also exits 1. (b) `[ -f "$NS/lock.flock" ]` only proves the test's *own* background holder subshell created that file, not that the updater opened it. Codex independently confirmed T57 would also pass if `flock` failed outright every time, since the holder still creates the file and the updater still exits nonzero for the wrong reason. Fix: use a manifest with a real, applicable release so an uncontended run would exit 0, then assert nonzero *and* grep captured stderr for the actual contention message (once Blocking #1 is fixed and stderr survives) — or at minimum assert on `current` being unchanged as the discriminator, not just RC.

4. **`export AU_LOCK_NO_FLOCK=1 AU_TEST_MODE=1` (global, `test-updater.sh:26`) pins T1–T56 onto the symlink fallback, and T57/T58's `else` branches call `ok` on skip** — inflating PASS count for tests that never ran. Verified on this actual review environment (macOS, no `flock` binary on PATH): **0 of 58 tests exercise the real production locking primitive this PR introduces.** The suite reports all-green while the production-critical code path is completely untested here. Fix: a `skip()` counter instead of `ok()` in the skip branches, and run this suite on a Linux runner (where `flock` is present) as part of CI for this file.

5. **`LOCK_FATAL=1` in `cmd_recovery` doesn't actually gate boot** (`aastar-node-updater.sh:444`, comment claims "让 systemd 可见,绝不静默跳过掉电回滚"). Checked `airaccount-updater-recovery.service` (pre-existing, not touched by this diff): `Before=kms-api.service` with no `Requires=`/`BindsTo=` anywhere in the tree — this is ordering-only. Confirmed via systemd dependency semantics (and independently by Codex): a failed oneshot unit under `Before=` alone does not block or delay the ordered-after unit — `kms-api.service` still starts against the un-rolled-back `current`. The exit-code hardening is still a real improvement (journal visibility, `systemctl status` reflects failure) but the comment overstates the delivered guarantee. Fix: either add `Requires=airaccount-updater-recovery.service` to the kms-api drop-in if boot must actually gate on rollback, or soften the comment to "仅提升可见性,不阻塞 boot".

### Low

6. Lock backend selection (`aastar-node-updater.sh:235-243`) is completely unlogged — a silent `command -v flock` miss (e.g. a restricted systemd unit `PATH`) sends a production host down the symlink-CAS path with zero journal trace, making a split-brain scenario undiagnosable after the fact. Suggest `log "lock backend: flock|symlink-cas"` right after selection.
7. T58 (split-brain guard test) only asserts "exit nonzero," never that the failure was specifically the split-brain `die` — same vacuity class as T57, just lower-stakes since the guard logic itself is otherwise sound. Grep stderr for "防 split-brain 双持" once #1 is fixed.

### Rejected (R1a false positives)
R1a flagged the `9>&-` fd-closing additions themselves (notify_send/fetch/run_health/restart_service) as bugs, reasoning that closing fd 9 in the child "releases the lock" — this inverts the actual mechanism. Closing fd 9 in the child *prevents* that child (and its descendants) from inheriting the flock reference; it does not touch the parent's own hold on the lock. These 4 fixes are correct and were confirmed clean by both R2 and R4.

### Suggestions
- Add a negative test that specifically catches Blocking #1: drive the flock path to a `die()` and assert stderr is non-empty / contains the red marker text. Without it, this exact regression can reappear on the next refactor unnoticed.
- Consider `flock -w <n>` instead of `-n` for `recovery` specifically — with `LOCK_FATAL=1` now wired in, a boot-time race that a short wait would resolve now hard-fails immediately, trading a silent-skip failure mode for a noisy-abort one at boot.
- The fallback-path hardening in this same diff (`lock_stale_min()`'s overflow/leading-zero clamping to [60,604800]s, `rm -rf` on moved-aside entries, re-verify-after-`ln -s`) is clean and correctly reasoned — no objections there.
