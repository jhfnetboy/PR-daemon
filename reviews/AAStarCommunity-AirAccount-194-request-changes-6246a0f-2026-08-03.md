## PK Review v4 — incremental round 7 (commit `6246a0f`, fixing round 6's REQUEST_CHANGES from `1a84889`)

**Verdict: REQUEST_CHANGES**

This commit correctly fixed round 6's 4 should-fix/nit items (pending retention on the unrecoverable rollback path, legacy-lock liveness check before blind delete, `T52` leading-zero pid coverage, the `return 0` fix so `acquire_lock`'s while-loop exit status doesn't kill the caller under `set -e`) — test suite run locally: **101/101 PASS, no regressions**. But the fix for round 6's 3 blocking findings (TOCTOU/double-hold class) closes the specific reported scenarios while leaving the same *class* of bug open in three new shapes, and the recovery-locking fix itself introduces a new regression: boot recovery can now silently no-op instead of rolling back.

### Blocking

1. **`cmd_recovery` calls `acquire_lock` without `LOCK_FATAL=1` — on contention it silently `exit 0`s instead of rolling back** (`:417`; contrast `cmd_apply` which sets `LOCK_FATAL=1` at `:672`). `lock_contended()`'s default branch (`:190-192`) is `warn "...退出"; exit 0`. Reproduced: seed `pending=0.29.0` + a lock symlink pointing at a live pid → run `recovery` → prints "另一个 updater 实例在跑", **exits 0**, `current` still points at the uncommitted release, `pending` untouched. Since `recovery.service` is presumably `Type=oneshot`/`RemainAfterExit=yes` with no `OnFailure=`, systemd sees success and the power-cut rollback this whole PR exists to guarantee is silently skipped. The trigger path is realistic, not exotic: a lock symlink left behind by a killed `apply` persists across reboot, and post-reboot pids are commonly reused quickly by unrelated processes — and this round's own fix bumped `LOCK_STALE_SECS` from 1h to **24h** (`:181`), which widens this exact misjudgment window by 24x. Fix: `LOCK_FATAL=1` before `acquire_lock` in `cmd_recovery` (boot-recovery failure must be visible to systemd), and consider qualifying the lock by boot identity (`/proc/sys/kernel/random/boot_id`, or a pid + start-time pair) instead of wall-clock age, so a lock from a previous boot is unconditionally stale rather than guessed at.

2. **Startup orphan sweep (`rm -f "$LOCK_LINK".stale.*` at `:222`, this round's fix for round-6 #6) deletes OTHER in-flight processes' moved-aside staging files, not just its own.** It's unconditional and cross-process. If process F starts `acquire_lock` while process A is mid-`reclaim_stale_lock` (between its `mv` at `:208` and its `readlink`/restore at `:211-214`), F's sweep deletes A's `.stale.$$` file. A's subsequent `readlink` then returns empty, and if that staged file happened to hold a *third party's live lock* that A's `mv` incidentally scooped up (see #3), that live lock reference is now gone permanently while its holder keeps running unaware. Fix: only sweep files whose embedded pid is provably dead (`readlink`-derived pid check + `kill -0`), never a blind `.stale.*` glob.

3. **`reclaim_stale_lock`'s `mv` steals whatever symlink currently occupies `$LOCK_LINK`, not the specific dead pid that was validated — and the restore-via-`ln` fix for round-6 #2 closes the *clobber* case but not the *double-hold* case.** Walkthrough: racer A reads `oldpid=D` (confirmed dead). Between A's read and A's `mv` (`:208`), legitimate live holder L successfully (re)acquires the lock via its own `ln -s "$$" "$LOCK_LINK"`. A's `mv` has no way to know this — `rename(2)` moves whatever is at the path regardless of content — so it silently steals L's live link into A's staging area. `$LOCK_LINK` is now vacant *while L is still inside its critical section believing it holds the lock*. If a 4th process E calls `acquire_lock` in that vacancy window, E's `ln -s "$$" "$LOCK_LINK"` succeeds — E now also holds. When A reaches its restore (`:214`, `ln -s "$moved" "$LOCK_LINK"`), it silently fails (`|| true`) because E already occupies the path, so L's reference is never restored. Net: L and E are both inside the critical section, and L's own `cleanup()` trap (`readlink "$LOCK_LINK" = "$$"`) can never detect this since the path now points to E. No re-verification step exists anywhere after a successful `ln -s "$$"` to catch this. Fix: immediately after any successful lock acquisition, re-`readlink` and confirm it's still `"$$"` before proceeding; structurally, this hand-rolled `ln`/`mv`/`readlink` CAS has now needed correction across rounds 5, 6, and 7 for variants of the same class — recommend switching the actual fleet's primitive to `flock(1)` (the real deployment target is Linux boards, which all have `flock` via util-linux; the "macOS has no flock" comment applies only to the dev/test host) or a boot-id-qualified lock, rather than continuing to patch the CAS-by-hand approach.

### Should fix

4. **`LOCK_STALE_SECS` validation (`:181`, this round's fix for round-6 #10) runs at top-level script scope, before `load_policy_env()` (`:99-106`, invoked from `main()` at `:750`) ever sources `$AU_ENV_FILE` (`:103`).** Any `LOCK_STALE_SECS` set via `updater.env` — the actual supported operator-configuration mechanism — completely bypasses this round's validation; it only protects a raw shell-env-var invocation. Fix: move the validation to run after `load_policy_env`, or re-validate inside `lock_is_old()` itself.

5. **Leading-zero `LOCK_STALE_SECS` values pass the digit-only validation but still hit bash's octal (mis)interpretation in `$(( LOCK_STALE_SECS/60 ))` (`:198`).** Mechanically reproduced: `x="089"; echo $(( x/60 ))` → `bash: 089: value too great for base`. In the actual call context (`lock_is_old && return 1` inside `lock_holder_alive`), `set -e` does not abort the script — the arithmetic error goes to stderr and `lock_is_old` ends up returning false, meaning **stale-lock detection silently stops triggering entirely** for any invocation with such a value (e.g. a padded `LOCK_STALE_SECS=086400`). Non-8/9 leading-zero values (e.g. `007`) don't error but get octal-reinterpreted, silently computing the wrong threshold. Fix: extend the validation case to also reject `0*` (same pattern already used in `lock_holder_alive`), or strip leading zeros / force base-10 with `$((10#$LOCK_STALE_SECS))`.

6. **Legacy mkdir-lock liveness guard only runs once, before the acquisition loop (`:225-232`) — a TOCTOU window lets it be bypassed entirely.** If an old-format lock directory gets created *after* this check runs but before the loop's `ln -s "$$" "$LOCK_LINK"` executes, `ln -s` targeting a directory succeeds by landing *inside* it (creates `$LOCK_LINK/$$`) and returns 0 — the while loop's condition is satisfied on the first try, the body never executes, and the process believes it holds an exclusive lock while a legacy-format holder is also alive underneath. Reproduced: pre-seed `$LOCK_LINK` as a directory containing a live pid's `pid` file: after `acquire_lock` returns, `$LOCK_LINK` is still a directory (not the caller's symlink), containing both the old pid file and the new `$$` entry the `ln` created inside it — a live double-hold that `cleanup()` (which checks `readlink "$LOCK_LINK" = "$$"`, false since it's a directory) can never clean up. Fix: after any successful `ln -s "$$" "$LOCK_LINK"`, verify `[ -L "$LOCK_LINK" ] && [ "$(readlink "$LOCK_LINK")" = "$$" ]` before proceeding; treat failure as needing to redo the legacy check.

7. **`reclaim_stale_lock` doesn't guard against `$LOCK_LINK` being a directory/regular file at the `mv` step** (`:208` + interaction with `:186`/`:222`). If the path is a directory, `mv` still succeeds, `readlink` on the moved-aside directory returns empty, and if `oldpid` was also empty, `moved = expected` short-circuits into "confirmed dead, clean it up" — but `rm -f` on a directory fails silently (`|| true` swallows it), leaving a permanent orphaned `.stale.<pid>/` directory that neither `cleanup()` nor the startup sweep (both `rm -f`) can ever remove. Fix: use `rm -rf` on that path, and/or check `-L` before treating the moved entry as a simple pid symlink.

8. **New test `T54` locks in the current (soon-to-be-wrong) behavior without asserting the exit code.** `kms/tests/updater/test-updater.sh:1001-1010` runs `recovery` under lock contention and only asserts `current`/`pending` are untouched — it never checks the process's exit status. Once Blocking #1 is fixed (`LOCK_FATAL=1`, hard failure), this test will keep "passing" without noticing the intended exit-code semantics changed, and would similarly have missed the current silent-`exit 0` regression if it had asserted the code. Fix: assert `recovery` exits non-zero under contention, and that an alert was attempted/queued.
