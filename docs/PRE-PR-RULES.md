# 提 PR 前的机械自检规则

> **这份文件的来源不是通用最佳实践，是我们自己 127 份 review 存档里 74 条阻断项的统计。**
> 每一条都对应一个真实返工过的 PR。目的只有一个：让 PR 一次过，而不是靠多跑几轮 review 抓出来。
>
> 用法:产 PR 的仓库把这份规则内化进它的开发 skill —— 开 PR 前逐条跑，跑不过就别提。
> 每条都标了「怎么机械检查」;做不到机械检查的条目不该出现在这份文件里。

## 阻断项分布(2026-08-05 统计，n=74)

| 类别 | 次数 | 对应规则 |
|---|---|---|
| 并发/竞争 | 15 | C |
| 文档/注释与实际行为不符 | 11 | B |
| 跨层不一致 | 10 | A |

| 全新部署/升级路径 | 4 | E |
| 测试假绿 / 不可逆破坏 / 输入未校验 | 7 | F |

## A. 跨层一致性(最大的复合类:A+B 合计 21/74)

**A1 — 改了「动词/操作/枚举」的分类，必须同时改掉每一处平行实现。**
一个操作在两处被分类，就一定会分叉。真实案例:`is_mutating` 只认 `apply|rollback`，把 `check`
当只读，而 updater 的 `cmd_check` 实际会装机 —— 同一个 commit 的 shell 层却给 `check` 加了验签断言，
两层对同一个动词判断相反。

机械检查:
```bash
# 找出在 >=2 个文件里出现的动词/操作名,逐个确认两侧分类一致
for v in $(grep -rhoE '"(apply|rollback|check|status)"' src/ | sort -u); do
  echo "== $v"; grep -rn "$v" src/ scripts/ *.sh 2>/dev/null
done
```
PR body 必须有一张「动词 × 每一层的分类」对照表。缺表 = 不该提。

**A2 — 改了 schema / 校验表达式,必须有「一侧产物喂另一侧校验器」的测试。**
两份手写 schema 第一天就会分叉。正确形态见 `AirAccount#196` 的 T1:signer 真签一个 manifest，
喂给节点真正的 `load_manifest`。

**A3 — 同一份 schema 不允许存在两份手写副本。** 抽成一个共享文件，两边都引用它。
这是 A1/A2 的共同根因,修它比反复对齐便宜。

**A4 — 密码学承诺/签名方案:字节对齐不够,还要证明「签的那一方在签的时刻拿得到每一个被签的字段」。**
真实案例:digest 两侧字节完全一致，但被签的 `index`/`ttl` 是服务端派生的，客户端根本算不出来 →
严格模式直接不可用。问自己:**签名时，签的那一方是否已经持有每一个被签字段?**

## B. 文档/注释与实际行为不符(11/74)

**B1 — 注释里写的行为断言必须有对应代码。**
真实案例:注释写「STATE_DIR/releases 存在才查」，但只有 `releases` 加了 `[ -e ]` 守卫，
`STATE_DIR` 在无守卫的循环里 —— 目录不存在时整个面板每个动词都挂。

机械检查:diff 里新增/改动的注释若含「才/仅/只在/不会/一定/必须」这类条件词，
同一个 hunk 内必须有对应的分支或断言。人工过一遍这类注释，逐条指出它对应哪一行代码。

**B2 — 引用的文档必须存在。**(纯机械,零判断，`Brood#36` 连续 4 轮栽在这)
```bash
# ⚠️ 只扫【本次 diff 改动的文件】,不要全仓库扫。
#    全仓库扫会把「引用别的仓库路径」的文件(review 存档、调研笔记、贴过来的日志)全报成悬空 ——
#    实测在 PR-Daemon 上直接产出 5+ 条误报,全部来自 reviews/ 里引用被审仓库的文档路径。
#    规则要能用,就必须没有噪声;有噪声的 lint 三天内就会被忽略。
git diff --name-only origin/<base>...HEAD | grep -E '\.(sh|md|rs|ts|py)$' | while read -r src; do
  grep -hoE '(reference|docs)/[a-zA-Z0-9._-]+\.md' "$src" 2>/dev/null | sort -u | while read -r f; do
    [ -f "$f" ] || echo "$src → 悬空引用: $f"
  done
done
```

**B3 — 删了一个能力,必须同步删掉所有对外宣传它的地方。**
真实案例:PR 删掉了 daemon 集成，但 `marketplace.json` 和 `plugin.json` 的描述还在卖它 ——
装插件的人被承诺了一个已经不存在的功能。

机械检查:PR 删除了某个脚本/子命令 → `grep -rn "<被删的名字>" --include='*.json' --include='*.md'`
必须零命中。

**B4 — 改了某文件的行为,grep 它在所有 `*.md` 里的出现并逐条确认。**

## C. 并发(15/74 — 单类最大)

**C1 — 任何「先检查 → 再 await/acquire → 再动作」的形状,拿到锁之后必须重新检查。**
真实案例(同一个仓库出现两次):STUCK 闩在 `acquire()` 之前检查 —— B 通过检查后阻塞等锁，
A 超时置闩并释放锁，B 带着过期的判断继续跑第二个 root 操作。登录锁定计数器是同一个形状。

机械检查:
```bash
# 找出 acquire/lock 之前就出现的状态检查
grep -n -B8 '\.acquire()\|\.lock()\|acquire_lock' src/**/*.rs \
  | grep -iE 'if .*(stuck|locked|closed|busy|pending|exists)'
```
命中即需要人工确认「这个检查在拿到锁之后有没有重做」。

**C2 — 新增/修改信号量、锁、闩、PID 文件、单例发现逻辑,必须有真跑并发调用的测试。**
顺序调用的单元测试测不出这类问题。锁保护了协调文件的读写，**不代表「要不要启动」这个决策也被序列化了**。

**C3 — `tokio::spawn` 里「await 之后再清理」的模式,必须专门写 panic 测试。**
正常路径和错误路径的测试都测不出「panic 会跳过清理」。真实案例:cancel token 永久泄漏 + run 卡死。

**C4 — 超时释放的 permit 不等于对方进程死了。**
`kill_on_drop` 的 SIGKILL 打不动已经 exec 进 root 子进程的 sudo(Linux 按当前 uid 判权)。
超时后必须 fail-closed，而不是让重试再起一个并发实例。

## D. fail-open(7/74)

**D1 — diff 里每新增一个 `|| true` / `2>/dev/null` / `catch {}` / `.unwrap_or(false)` / `|| echo <默认值>`，
PR body 必须逐个说明「失败时放行是否安全」。**

机械检查:
```bash
git diff origin/<base>...HEAD | grep -nE '^\+.*(\|\| true|2>/dev/null|catch \{\s*\}|unwrap_or\(false\)|\|\| echo)'
```
每一条命中都要在 PR body 里有一行说明。

**D2 — 信任边界上的检查不允许「取不到就跳过」。**
真实案例:基线回读 curl 失败时静默降级到本地基线 → 新 clone 上一次网络抖动就签出错误的计数器，
全网永久拒绝更新。「取不到」和「确实不存在」必须区分:前者中止，后者要求显式的 `--no-baseline` 之类的选项。

**D3 — 签发/验签环节不允许有「跳过验证」的分支。** 缺公钥应该是硬失败，不是 `if [ -f "$PUB" ]`。

## E. 全新部署 / 已部署节点升级(4/74，但每次都是 High)

**E1 — 改了会读写目录/文件的部署脚本,必须在「空目录 / 从没跑过」的状态下真跑一遍。**
真实案例:`ReadWritePaths` 指向一个 README 从没创建过的目录 → `systemctl start` 直接 226/NAMESPACE。

**E2 — 新增了「某目录/文件必须预先存在」的前置要求,必须同时回答两个问题:**
1. fresh deploy 怎么创建它?(README 步骤)
2. **已经部署在跑的节点怎么升级?**(这一条最常被漏 —— 修好了新装，老节点全挂)

**E3 — 每一个新的前置要求,反过来检查「它不存在时会发生什么」。**
是整个服务不启动，还是只有相关功能降级? 只读操作(status/诊断)不该因为写路径的前置缺失而挂掉。

## F. 测试质量 + 平台

**F1 — 断言「这个命令应该失败」的测试,必须断言具体错误信息,不能只断言非零退出码。**
真实案例:测试套件报 `PASS=6 FAIL=0`，实际上 3 条断言永远为真 —— 因为脚本在那个平台上
**每次**都以非零退出，测试根本分不清「正确拒绝」和「崩了」。

**F2 — 每个测试套件必须有一条 rc=0 的正向对照。** 没有正向对照，就无法证明失败断言测的是失败本身。

**F3 — shell 脚本必须在 `/bin/bash` 下跑一次,不只是 PATH 上的 bash。**
macOS 自带的是 **bash 3.2.57**，行为和 bash 5 有实质差异，而发版/签名往往就在 Mac 上做。

**F4 —(本仓库特有,纯机械)`$VAR` 后面紧跟中文/全角字符必须加花括号。**
bash 3.2 的变量名扫描不认多字节，会把后面那个字吃进变量名，`set -u` 下直接 `unbound variable`。
真实案例:`echo "未写 $OUT、未签名"` 让 `--dry-run` 在 macOS 上 100% 崩溃，而私钥就在那台机器上。
```bash
LC_ALL=C grep -rnE '\$[A-Za-z_][A-Za-z0-9_]*[^ -~]' --include='*.sh' .
```
**这条应该直接进 CI**,它零误报成本、零判断。

**F5 — 改了 `.github/workflows/*.yml`,除了手动跑步骤命令,必须用 `yaml.safe_load` 真解析文件本身。**
手动模拟步骤命令抓不到 YAML 语法错误。

**F6 — CI 命令在本地也跑不过时,别默默换个能跑的写法。** 那本身就是一个真发现。

## G. 提 PR 时必须写进 body 的东西

1. **验收命令 + 真实运行输出**(不是「应该能过」，是贴出来的输出)
2. **跨层对照表**(若命中 A1)
3. **每个新增 fail-open 的安全性说明**(若命中 D1)
4. **已部署节点的升级路径**(若命中 E2)
5. **本次没做但相关的事** —— 明说，别让 reviewer 去猜是漏了还是故意的

## 用不上这份文件的情况

纯文档 PR(只改人读的散文、README、任务描述)不适用 A/C/D/E。但**自动化会读的文件不算纯文档** ——
CI workflow、`.pilot.yml`、被脚本解析的任务/规划 ledger,这些是 Markdown 但不是给人看的，全套规则照用。
